# ADR-001 — Raft Implementation

**Status:** Accepted

## Context

The model registry requires a consensus mechanism to establish a single authoritative order for model promotions and to ensure that commited promotions survive the failure of the node that accepted them.

Two approaches were considered: use an establish consensus implementation such as etcd or Consul, or implement the Raft consensus core as part of this project.

Using an established implementation would reduce implmentation and operational risk, but would
also hide the consensus layer that is central to the project's purpose. This project is intended to study
the behaviour of a small distributed registry under failures, rather than only consume a consensus-backend
service.

## Decision

The project will implement its own Raft consensus core based directly on the Raft paper, *In Search of an Understandable Consensus Algorithm*.

The Raft implementation will be isolated in the `raft/` package and will have no knowladge of fraud scoring, model artifacts, HTTP, or the registry's application-level state. The registry will use the Raft
package as a generic consensus mechanism and provide the application-specific state machine above
it.

## Consequences

This decision gives the project direct control over the visibility into leader election, log replication,
commitment, persistence, and recovery. It also keeps the consensus core resusable and independent of
the fraud-scoring application.

The trade-off is substantially higher implementation and correctness risk than using an established
consensus implementation. The project therefore accepts additional development and testing effort in
exchange for making consensus itself an explicit part os the system being studied.

This implementation is an educational and engineering exercise and is not assumed to provide the maturity or operational guarantees of established production consensus systems.
