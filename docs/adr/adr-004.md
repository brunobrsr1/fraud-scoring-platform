# ADR-004 — Scoring API Contract

**Status:** Accepted

## Context

The `/v1/score` endpoint is responsible for scoring transactions using the currently active model. The current model expects 30 numerical features (`Time`, `V1`–`V28`, `Amount`). Business-level fields such as `user_id`, `currency` and `merchant_category_code` are not consumed by the model and no feature-engineering or enrichment layer is currently implemented in the scoring service.

The API must also remain deterministic and safe when different model versions are temporarily served by different nodes during registry convergence.

## Decision

`POST /v1/score` will accept a `transaction_id` and a named map of model-ready features:

```json
{
  "transaction_id": "tx_987654321alpha",
  "features": {
    "Time": 55810.0,
    "V1": -1.359807,
    "V2": -0.072781,
    "...": "...",
    "V28": -0.021053,
    "Amount": 149.62
  }
}
```

The server will construct the model input vector according to the `feature_order` stored in the loaded model artifact. The request must contain every required feature exactly once and must not contain unknown features. Missing, `null`, non-numeric, `NaN` or infinite values result in `400 Bad Request`.

The `feature_order` is an immutable property of the model schema. A model may change its weights and intercept between versions, but a promoted model must preserve the active feature order. The registry will enforce this invariant when validating model promotions.

The response will include the `transaction_id`, the computed `score`, and metadata identifying the model version and registry synchronization state. Scores will be returned as `float64` without deliberate rounding.

Business-level fields are intentionally excluded from this endpoint. If feature engineering or business-level transaction processing is introduced later, it will be provided by an upstream layer rather than implicitly added to the scoring contract.

## Consequences

This design keeps `/v1/score` closely aligned with the current model artifact and avoids duplicating the model's feature order in application code. Strict validation prevents malformed requests from silently producing incorrect scores.

Making the feature schema immutable simplifies model promotion and prevents different nodes during convergence from accepting different request schemas. The trade-off is that models requiring a different feature schema cannot be promoted through the existing contract; such a change requires a new API/schema version or a coordinated breaking change.
